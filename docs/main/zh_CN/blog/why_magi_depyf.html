为什么需要 magi_depyf#

magi_depyf 是 MagiCompiler 的编译可观测性层。它回答三个实际问题：

  1. 编译过程中究竟发生了什么？

  2. 结果是否符合预期？（例如：图切分形状、缓存复用、重试行为）

  3. 如果出错了，我应该先看哪里？

1. Positioning: Built-in observability for MagiCompiler#

在真实的 MagiCompiler 流水线中，编译跨越多个阶段：Dynamo 捕获、Magi 后端图变换/切分、Inductor 代码生成，以及 AOT/JIT 复用。仅靠普通日志往往难以可靠地回答：

  • 失败发生在全图层面，还是某个具体的子图中？

  • 某个 pass 是否意外改变了图的行为？

  • 这次运行为什么没有命中缓存？

magi_depyf 将这些信号以结构化的事件与产物形式写入磁盘，让你可以确定性地回放、对比与调试。

2. Primary scenario: magi_compile#

2.1 推荐的使用方式#

对于 magi_compile 用户，magi_depyf 作为内建可观测性层最为实用：

  • 在编译期间将事件流式写入 timeline_events/timeline.jsonl

  • 将事件产物写入 timeline_events/files/ 目录

  • 导出结构化的 compiled_functions/ 产物树

大多数情况下你无需手动挂接自定义 hook。走完整的 MagiCompiler 路径，然后查看输出目录即可。

2.2 在 Magi 编译路径下你会自动获得什么#

在 magi_compile 场景下，你无需手动调用 explain_compilation。只要模型走完 MagiCompiler 路径，magi_depyf 的输出就会被自动写入。

例如，某次真实运行产生了：

  • magi_depyf_torch_compile_debug/magi_depyf/run_20260322_192147/model_1_TwoLayerTransformer_rank_0/timeline_events

一般来说，输出的目录模式为：

  • <cache_root_dir>/magi_depyf/run_*/model_*_rank_*/timeline_events/

该目录下的关键产物：

  • timeline.jsonl：编译期间写入的流式事件日志

  • files/0000_*、files/0001_*、…… 带附属产物的事件文件夹

  • files/*/attributes.json：每个事件文件夹的结构化元数据

相关的编译产物视图还会输出到：

  • <cache_root_dir>/magi_depyf/run_*/model_*_rank_*/compiled_functions/

完整可运行示例见：

  • magi_compiler/magi_depyf/example/magi_compile_transformer_example.py

这条路径能快速回答的典型问题：

  • 全图/子图事件是否按预期顺序发生？

  • 是哪个 pass 改变了图结构？

  • 是否发生了 RestartAnalysis，缓存加载是否如预期被跳过？

  • 哪个事件文件夹包含用于调试的精确图/代码快照？

3. Secondary scenario: plain torch.compile (manual entry)#

magi_depyf 同样适用于纯 torch.compile，但这是次要工作流，需要手动包裹上下文：

import torch

from magi_compiler.magi_depyf.inspect import explain_compilation


@torch.compile
def toy_example(a, b):
    x = a / (torch.abs(a) + 1)
    if b.sum() < 0:
        b = -b
    return x * b


with explain_compilation("./magi_depyf_torch_compile_debug"):
    for _ in range(10):
        toy_example(torch.randn(10), torch.randn(10))

具体示例见此处：

  • magi_compiler/magi_depyf/example/torch_compile_toy_example.py

该示例展示了在纯 torch.compile 场景下使用 explain_compilation 的最简方式。

4. Event model (concise)#

每个事件包含：

  • name：事件名称（带 fullgraph_ 或 subgraph_N_ 前缀）

  • attributes：结构化元数据（例如 lifecycle_name、runtime_shape、graph_index、reason）

  • files：附属的文本产物（图代码、inductor 输出等）

4.1 生命周期命名模式#

生命周期事件被规范化为以下模式：

  • *_before_<lifecycle_name>

  • *_after_<lifecycle_name>

  • *_failed_<lifecycle_name>

  • *_skip_<lifecycle_name>

其中 * 为 fullgraph 或 subgraph_<N>。

4.2 代表性示例#

  • fullgraph_before_graph_split

  • fullgraph_after_graph_split

  • fullgraph_before_compiler_manager_compile

  • fullgraph_after_compiler_manager_load

  • subgraph_2_before_postcleanuppass

  • subgraph_2_after_postcleanuppass

5. Output layout (current implementation)#

debug_output/
  timeline_events/
    timeline.jsonl
    files/
      0000_fullgraph_.../
        attributes.json
        *.py / *.txt
      0001_subgraph_.../
        submod_<N>/
          attributes.json
          *.py / *.txt

  compiled_functions/
    <function_name>/
      overview.md
      decompiled_code.py
      entry_0/
        guards.txt
        compiled_fns/
        piecewise_subgraphs/

6. Recommended triage order#

调试编译问题时，按以下顺序进行：

  1. timeline.jsonl：先核对事件顺序

  2. *_failed_* / 缓存相关的生命周期事件（compiler_manager_load、compiler_manager_cache_store）

  3. 相关事件附带的图文件：核对 pass 前后的图状态

  4. compiled_functions/*/overview.md：核对最终的编译产物结构

关键不只是绝对耗时，而是：

  • 发生了什么，

  • 是否符合预期，

  • 以及失败时应深入到哪里排查。

7. Compatibility and entry-point summary#

  • 主入口：MagiCompiler 主路径（magi_compile）

  • 可选入口：纯 torch.compile + 手动 explain_compilation

一句话总结：

magi_depyf 首先是 MagiCompiler 的内部可观测性基础设施，同时在需要时也可作为纯 torch.compile 的手动排障工具使用。
